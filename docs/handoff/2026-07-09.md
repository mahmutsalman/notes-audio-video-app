# Handoff — 2026-07-09 [11:30]

## Session Goal
Add a Capture-tab button that clears captures off the board without deleting them, so the board can
be reset before going live on stream. Requirement was explicit: keep them in the database, keep the
tags, keep them findable. Build and install.

## What Got Done
- `86bc3d7` fix(capture): committed the 2026-07-07 `AUTO_DELETE_ENABLED = false` safeguard that had
  been shipped to the installed app but never committed. `getExpired()` returns `[]`, so neither the
  startup sweep nor the `quickCaptures:cleanup` IPC deletes anything.
- `0e8f693` feat(capture): archive instead of delete.
  - Migration: nullable `quick_captures.archived_at` (idempotent PRAGMA guard).
  - Ops: `archiveAll()`, `unarchive(ids)`, `getArchived()`, shared `_hydrate()`.
  - IPC + preload + `ElectronAPI` types for the three new channels.
  - `CapturePage`: "Clear board" button, Board/Archived tabs, post-clear Undo banner.
  - `CaptureItem`: archived badge + Restore button; removed the "expires in Nd" badge.
  - `CapturePage` no longer calls the destructive `quickCaptures:cleanup` IPC.
- ADR-0004 written.
- Reference docs corrected — FR-16, NFR-04, `architecture.md` (x3), `glossary.md`, `use-cases.md` (x2)
  all still claimed a 7-day TTL. These four files are individually gitignored, so the fixes are on
  disk but not tracked. They are what `CLAUDE.md`'s `@./docs/*` imports read each session.
- Built and installed to /Applications. Migration confirmed applied against the live DB; 1 capture,
  49 images, 0 archived, nothing lost.

## What Was Tried and Abandoned
- **Approach**: filter only the capture-list query (`getRecent`) on `archived_at IS NULL`.
  - **Why we walked back**: the production DB is a single `quick_captures` row holding all 49 images,
    because `getOrCreate()` funnels every paste within the window into one package. With only the
    list query filtered, the next paste after clearing would have called `getOrCreate()`, found the
    archived capture, reopened it, and dragged all 49 images back onto the board.
  - **Lesson**: when a table has more than one read path, a visibility flag has to be enforced on
    every one of them. Found by reading `getOrCreate()` before writing code, not by testing after.
- **Approach**: keep the existing silent 7-day board filter alongside the new Clear button.
  - **Why we walked back**: user chose the purely-manual board. A silent time-based disappearance is
    the same anti-pattern that caused the original data loss — the user cannot tell "hidden" from
    "gone". Removed the window, the badge, and the subtitle.
- **Approach**: press "Clear board" in the running app to verify end-to-end.
  - **Why we walked back**: it would archive 49 live images while the user is streaming. Verified the
    lifecycle against a copy of the production DB instead. Left as the top item in Next Concrete Action.

## Decisions Made
- ADR-0004: Quick Capture hides by archiving, never by deleting or expiring. Rewrites FR-16 and
  generalizes NFR-04 to "no user-authored content is ever deleted on a timer; hiding is always
  reversible." This now governs any future TTL / cache-eviction / "temporary space" proposal.

# Handoff — 2026-07-09 [22:00 session]

## Session Goal
Support many reflective notes per review instead of one, on both prompts: Enter logs a note and
starts the next. Persist them properly. (Images on review notes deferred to the next session.)

## What Got Done
- `2517d4f` feat(echo): Mahmut's own in-progress work, committed unmodified and on its own —
  Cmd/Ctrl+wheel zoom + pan of the review image, the mask hit-test fix that zoom exposed
  (it assumed the canvas rendered 1:1), MaskEditor hint moved off the image, TagAutocomplete
  opt-out `autoFocus`, `input-glow` keyframes, and the `clean` script before every build.
- `2111181` feat(echo): `review_notes` table + multi-note UI + ADR-0005.
  - Enter logs the current note and starts a fresh one, on BOTH prompts. Notes stack above
    their box, numbered, each with a hover delete.
  - Notes are written the instant Enter is pressed, as drafts (`review_event_id IS NULL`)
    belonging to the card. Rating adopts them in the same transaction that writes the event.
  - Rating also flushes text left un-Entered in a box.
  - Echo detail page rewritten to render / add / delete the note list per past review.
  - `reviewEvents:updateNote` removed outright (op + IPC handler + preload bridge).
  - Legacy `review_events.note` / `.missed_points` backfilled once (21 notes from 17 events),
    then frozen: never read, never written, not dropped.
- Built, signed, installed. Migration confirmed against the live DB.

## What Was Tried and Abandoned
- **Approach**: keep notes in memory until the card is rated (the status quo, just as a list).
  - **Why we walked back**: Mahmut chose persist-on-Enter once shown that the existing code
    silently destroyed notes — both textareas reset in a `useEffect` keyed on the card id, so
    typing a note and pressing ←/→ wiped it, and abandoning a card discarded it. Meanwhile the
    placeholder had always read "(Enter to log)" while Enter only replayed a CSS glow.
  - **Lesson**: the UI was already promising the feature. Read what the placeholder claims.
- **Approach**: a second IPC call `reviewNotes.attachToEvent(noteId, eventId)` for notes added
  to a past review from the detail page.
  - **Why we walked back**: `add()` taking an optional `reviewEventId` does it in one round-trip.
- **Approach**: driving the review UI myself to verify. Guessed wrong twice on the nav icons and
  stopped — the rating buttons sit directly under the note boxes and a stray click writes a real
  FSRS rating. Mahmut verified it instead (screenshot), and the DB confirmed it end-to-end.

## Decisions Made
- ADR-0005: Many reflective notes per review, written on Enter. Notes address the CARD first
  (`review_item_id`), and the event adopts them at rating time — because no event exists while
  the user is typing. The adopting UPDATE is scoped `review_item_id = ? AND review_event_id IS NULL`.
